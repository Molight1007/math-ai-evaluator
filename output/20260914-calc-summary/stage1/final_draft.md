## 二、平台硬约束与时间系统重设

### 2.1 认知纠正（本阶段最重要的结论）

此前长期存在三个错误认知，本阶段逐条推翻：

| 旧认知 | 事实 | 证据来源 |
|---|---|---|
| 平台不设单题时限，1200s 是我们自设的 | **错误**。单题独立进程组有 1200s 硬时限，超时**杀整个进程组、不保证 finally**，该题计 C（0 分） | 官方 baseline README |
| 平台限时 6.5 小时 | **错误**。Agent 阶段总硬限为 **6h**（不含 Judge） | 同上 |
| 加时间能提高正确率 | **错误**。实测 >1150s 档正确率仅 10.8%，低于整体 | 195 题 `stage_timers` |

⇒ 真约束是 `6h × 3 ÷ 112 ≈ 578s/题`，**超时与异常都计 C 且分母不变**。

### 2.2 单题硬限的三次调整

| 时间 | 值 | 触发原因 |
|---|---|---|
| 9/13 早 | 1150 | 初始值 |
| 9/13 二轮 | **1000** | 实测 `official112-000` 跑了 1201s，越过 1200s 硬墙 |
| 9/14 00:29 | **1150** | 超时改为「不再重试」后，单次在途调用最坏 360s → 120s，压缩前提不再成立 |
| 9/14 11:55 | **1100** | 两轮实测再次越墙：并发 3 轮 000 = 1164.7s；并发 1 轮 014 = **1211.0s** |

**最终口径**：`max_time_per_question = 1100`，但 `tier_budget.deep` **刻意保持 1150 不动**。
两者职责不同：前者是「最后硬限」，只负责不许越 1200s 墙；后者是「资源分配」，
若跟着压到 1100，会**提前掐断本可在 1200s 内跑完的题**。生效值 = `min(deadline, tier_cap, pacer)`。

配置项：`max_total_time_seconds = 20700`、`paper_target_time = 19500`、
`tier_budget = {300, 750, 1150}`。

### 2.3 时间语义的护栏化

- `3_solve` 阶段上限曾设为 1200s（大于单题预算）⇒ `min(deadline, now+1200)` 恒等于 deadline，
  **阶段护栏形同失效**，导致 2.7 让出的时间被 3_solve 全部吸收。已修正为实测上限口径。
- `6_format` 阶段曾因 `gen_time_up()` 误用而**恒跳过**（护栏反而永久生效），修复后恢复正常。
- 给 `DeterministicChecker`（被 3.6 / 4_verify / 6.5 三处各跑一次）加内部超时护栏，
  此前实测出现过 **460s / 116s 的单次极值**，一次 460s 就吃掉单题预算的 40%。

## 三、开销收敛：省了哪些时间

审计依据是 195 题的 `diag.stage_timers`（去重口径）。**注意：以下为「机制 → 实测耗时」，不是「省下的时间」的等号，其中只有一部分拿到了直接的省时证据。**

| 环节 | 实测耗时 | 处置 | 依据强度 |
|---|---|---|---|
| `6_format` 差分检测 | 352–364s（1.9% 的题） | 加时间护栏 + 收敛参数 | 强（撞 180s 超时并重试，数值精确吻合 2×180s） |
| `3.6_audit_filter` Lean 三往返 | 200–580s（14.2% 的题） | 关掉 goal / multi_attempt / hover（对 verdict 零贡献） | 强（有 `480.4s` 日志实证） |
| `2.7_subgoal_main` | p50 630s（占单题 51%） | 关 `enable_skeleton_review` / `enable_dag_replan` | 中（本轮 2.7 已降至 135–337s） |
| `3.4_collab` | 最大 691s（**但当前配置下已不触发**） | 加阶段预算 + 与 3.3 共享改进额度 | **A/B 已完成 → 无效对照（见 3.3）** |
| `enable_calc_prewarm` | 30–111s/题 | **默认关闭** | 强（12 题实测只有 1 题与答案相关） |

### 3.1 一处必须纠正的过度归因

曾有结论称「NEW 代际单题均值 1231s、**45% 的题 ≥1200s 撞墙**」。经复核**不成立**：
那 36 条 ≥1200s 的记录全部来自 9/12–9/13 的**高上限实验轮**（当时上限被人为放开），
不代表生产配置下的真实分布。

### 3.2 明确「不砍」的环节

- **3.3 自改进（Step2）**：有正面证据（论文实测 22.2% → 31.1%；
  `ab_improve` 14/45 = 31.1%，最优组合 `ab_review` 16/45 = 35.6% 亦包含 Step2）⇒ **绝不能关**。
- **4.6 对抗式验证**：可砍清单中唯一呈**正向**的环节。

### 3.3 `3.4_collab` A/B 的结论：**无效对照，不能下结论**

**实验设计**：armA = `enable_collaborative_deep=false`（关），armB = 默认（开）；
其余配置逐字相同（cap 1100 / tier 300,750,1150 / `LEAN_BACKEND=bridge` / 并发 3）；
题单 5 题，均为**错题且历史上真触发过** `3.4_collab`，按 collab 历史最大耗时排序。

**结果（两臂各 5/5 完成）**：

| 题 | armA（关） | armB（开） |
|---|---|---|
| 004 | ❌ 1106.8s，tier=deep，3.4=**0.0s** | ❌ 1105.0s，tier=deep，3.4=**0.0s** |
| 064 | ❌ 1111.3s，tier=deep，3.4=0.0s | ❌ 567.3s，tier=**standard**，3.4=0.0s |
| 015 | ❌ 793.8s，tier=**standard**，3.4=0.0s | ❌ 1010.9s，tier=deep，3.4=0.0s |
| 088 | ✅ 335.3s，tier=standard，3.4=0.0s | ✅ 393.8s，tier=standard，3.4=0.0s |
| 000 | ❌ 799.2s，tier=standard，3.4=0.0s | ❌ 884.6s，tier=standard，3.4=0.0s |
| **合计** | **1/5** | **1/5** |

**为什么这个对照无效**：`3.4_collab` 在 **armB 上也没有执行** ——
10 次观测（2 臂 × 5 题）的 `3.4_collab` 耗时**全部为 0.0s**。原因是双重的：

1. 5 题里有 3–4 题的档位是 `standard`，**按设计就不会触发** 3.4（只有 deep 档才跑）；
2. 真正被判为 deep 的题，到达 3.4 时**生成侧时间截止已过**，被门控跳过
   （例：004 = `2.7` 355s + `3_solve` 243s 已 ≈ 600s，之后还要留 `3.6` 121s + `4_verify` 383s）。

⇒ 两臂**实质上都是「无 3.4」**。此时比对正确率（1/5 vs 1/5）看似"无影响"，
但那只是**假阴性**：机制在两臂都没跑。

**由此得出的两个更有价值的结论**：

- **`3.4_collab` 在当前配置下已经基本不触发** ⇒
  「关掉它省时间」的前提**不成立**（它几乎不消耗时间），**关也关不出收益，不关也没有损失**。
  历史记录里 121–691s 的耗时来自**旧配置**（高上限、未给 3.3 设预算帽、旧档位阈值）。
- ★★ **档位分类不稳定**：同一道题、同一份代码，`064` 在 armA 判 deep 而 armB 判 standard，
  `015` 则相反。这会**破坏所有"按档位分配预算"的机制**，也让任何配对对照失去可比性。
  这是比 3.4 更值得优先处理的问题。

## 四、★ 专项：本地精确计算器（工具计算）链路的问题分析

> 本节是全文重点。用户的核心诉求是「让大模型在解题过程中使用本地精确计算器，
> 降低计算错误」。**结论先行：链路本身已经修好，但模型仍然不用它 —— 障碍不在工具，在「模型默认心算」。**

### 4.1 问题全景

工具计算链路共暴露出 **7 个层次的问题**，且它们是**串行掩蔽**的 ——
每修掉上一层，下一层才会显形：

| # | 问题 | 性质 | 状态 |
|---|---|---|---|
| 1 | 「模型不写 `<calc>`」是**量错字段** | 观测错误 | 已纠正 |
| 2 | 模型其实在写，但**格式几乎全被工具拒收** | 工具解析过窄 | 已修 |
| 3 | 提示词**承诺了工具做不到的事** | 内部自相矛盾 | 已修 |
| 4 | 解析器**静默丢值** | 数据丢失 | 已修 |
| 5 | 埋点 `calc_tool_calls` **结构性恒空** | 观测错误 | 已修 |
| 6 | 方案 B（生成前猜算式）**前提不成立** | 设计缺陷 | 已关闭 |
| 7 | 下游连带：**Lean 系统验算提不出命题** | 级联失效 | 已缓解 |

### 4.2 问题一：「模型不写 `<calc>`」——这是量错字段造成的假象

**旧结论**：`<calc>` 在全库出现 **0 次**，说明模型拒绝使用工具。

**真相**：该统计读取的是 `response` 字段，而它**只存最终答案串**，
中间过程与工具标记根本不在里面。改用正确口径（`diag.calc_fallback` 埋点 +
回填产物 `[计算] expr = 结果`）后：

> 全库命中 **78/1270** —— **模型确实在写 `<calc>`**。

⇒ 这是一个纯观测错误，却直接导致了一轮错误的归因方向。

### 4.3 问题二：模型写了，但格式几乎全被工具拒收

对 78 次命中逐条统计拒收原因：

| 拒收原因 | 次数 |
|---|---|
| 「只支持单个数学表达式」（多行 / 代码块） | **133** |
| 整数字面量过大 | 37 |
| 「不支持 sin()」 | 26 |
| 表达式过长 | 14 |
| tan() / integral() / sum() | 8 / 4 / 2 |

**实证模型实际写的是什么**：

- `official112-016` v5，4 个 `<calc>` 全是 **Python**：
  `n = 20`、`x = [1]*10 + [-1]*10`、`S = sum(x)`、`print(...)`；
- `official112-016` v7：`<calc>19 < 20</calc>`（**比较式**）→ 报错「不允许的语法节点: Compare」；
- `official112-010`：`<calc># 验证…\nfrom sympy import…</calc>`（**Python 多行**）。

⇒ 模型把 `<calc>` 当成了「代码执行沙箱」，而工具只接受**单个数学表达式**。
这是**契约不一致**，不是模型不配合。

**修复（`agent/calc_tool.py`）**：加**降级解析**，让工具接受模型真实写出的形态 ——
支持多行、赋值链、注释行、`print()` 包裹。

### 4.4 问题三：降级解析仍失败 6/8 —— 根因是「多目标赋值」

降级解析上线后，用真实数据回放**仍然 6/8 失败**，逐个定位后找到明确根因：

> **不支持「多目标赋值」（tuple unpacking）**：`a, b, c = 1, 2, 3`

真实数据佐证：`official112-010` 一轮中写的是
`p1, q1, r1, s1 = 1, 0, -1, 0` 这种四元组解包，直接被拒。

**修复后的实测结果**：

| 输入 | 结果 |
|---|---|
| `n = 20` + `comb(n,3)` | **1140** ✅ |
| `x = 10` + `x*2` | **20** ✅ |
| `25*4+1` | **101** ✅ |
| `S = sum(k,1,n)` + `print(S)` | `n**2/2 + n/2` ✅ |

### 4.5 问题四：提示词承诺了工具做不到的事（内部自相矛盾）

同一份提示词常量里同时存在两条互相打架的指令：

- 「**必须写 `<calc>`（严禁心算）**」的清单里含 **三角函数 `sin/cos/tan`、`prod`**；
- 但「可用函数」清单与工具白名单 `_FUNCS` **都没有这些函数**；
- 而同一个常量在另一处又自述「三角 sin/cos 等**无通用精确值**」。

**实测后果**：26 次「不支持 sin()」、8 次 tan()、4 次 integral()、2 次 sum() 被拒 ——
模型照着提示词写，工具照着白名单拒。

**修复**：统一口径为「**工具能力外 → 不要写 `<calc>`**」，并把该引导补齐到
**全部 6 条生成路径**（此前只注入 3 处；漏了 revise、proof 等路径，
而「只改一处路径 = 没改」是本项目的既有教训）。

### 4.6 问题五：解析器静默丢值

在真实存档里统计 `[计算]` 行共约 **166 条**，其中 **13 条不在行首**
（例如夹在句子里）。而旧实现用 `head.startswith("[计算]")` 判断 ⇒
**这 13 条的值被静默丢弃**，且没有任何告警。

另有「散文吞值」问题：块体内混入自然语言时，旧逻辑会把数值一起吞掉。

**修复**：`head.startswith` 改为逐行 `find` 定位；新增 `_calc_prose_cut`
**只截断散文、绝不丢值**；并加两道防误匹配（块体须能切出 `=`；
结果须过 `_CALC_VALUE_RE`，禁 `" : ; \`` 等 JSON/代码标点且不含中英文散文）。

### 4.7 问题六：埋点坏了，看不见真相

`diag.calc_tool_calls` 字段由 `_collect_diag()` 按 `step == "calc_tool_call"` 导出，
但**全代码库从未 record 过这个 step 名** ⇒ 该字段**结构性恒空**，
会被读成「工具从来没成功算过」。这在本阶段已**误导读过一次归因**。

**修复**：新增 `BaseAgent.record_calc_successes()`（与记录失败的 `audit_calc_fallbacks`
镜像，只收非 `WARN:` / `ERROR:` 项），并在 **7 处** `<calc>` 求解点各补一行调用。

### 4.8 问题七：方案 B（生成前猜算式）前提不成立

方案 B（`2.65_calc_prewarm`）的思路是：让模型在解题**前**凭题面猜出该算什么，
由系统先把精确值算好摆在它面前。

**12 题错题回归实测**：

- 12/12 题都成功产出了预计算 —— 机制**确实触发了**；
- 但**只有 1 题**算出的算式与最终答案相关；
- 成本 30–111s/题，而单题预算只有 1150s。

⇒ 「让模型凭题面猜该算什么」这个**前提本身不成立**。已默认关闭
（字段保留，可 `--enable_calc_prewarm true` 开回）。

### 4.9 问题八：下游连带 —— Lean 的系统验算提不出命题

这是工具计算问题**最有价值的连带影响**：

Lean 侧有一条**不依赖 LLM** 的验算通道 `_verify_answer_by_system`：
它从 reasoning 里抽 `<calc>` / `[计算]` 算式，由系统构造 `(算式) = (答案数值)`
再交给 Lean 编译（`norm_num`）。

由于模型极少写 `<calc>`，这条通道**永远提不出命题** ⇒ 只能退回 LLM 翻译 ⇒
翻译环节的 LLM 调用超时（`LLMClient` 180s × 重试）⇒ 异常被 `except` **静默吞掉** ⇒
返回 `unknown` ⇒ **Lean 这道防线完全空转**（既不确认正确候选、也不淘汰错误候选）。

实测证据：`official112-016` 的 6 条 verdict **全部是 `unknown` + `degraded=lenient_pass`**。

**修复**：在 `except` 兜底里优先走系统验算通道（不依赖 LLM）——
返回 True → `answer_valid`；返回 False → `proof_invalid`；而不是一律降级为 `unknown`。

### 4.10 为什么「计算链路一直没用起来」—— 最终归因

把所有层拆开后，因果链是清晰的一条：

```text
模型默认心算
   ↓（提示词口头要求用工具，无强制力）
极少主动写 <calc>
   ↓（即便写了）
格式与工具契约不一致 → 被拒
   ↓（好不容易解析出的值）
静默丢值 / 埋点恒空 → 看不见、也没进答案
   ↓
Lean 系统验算提不出命题 → 退回 LLM 翻译 → 超时被吞 → verdict 全 unknown
```

**关键判断**：提示词已一致、工具能力已够、格式也已放宽，
**障碍不是「工具不能用」，而是「模型默认心算」**。
所以正确方向是**代码强制**（例如 `answer_selfcheck` 强制重问、或对高危运算
强制路由到工具），而**不是继续写更长的提示词请求**。

**当前状态（诚实标注）**：
计算链路对正确率的提升**尚未取得任何证据** —— 12 题错题回归里工具调用仍为零；
论文中 22.2% → 31.1% 的增益来自 **Step2 自改进**，与工具计算无关。

## 五、Lean 链路修复

| 问题 | 根因 | 修复 |
|---|---|---|
| Lean 双通道被**整体静默禁用**（镜像侧） | 「同步主仓」把 `lean_bridge.py` 覆写成缺 5 个定义的版本，而 `lean_gate.py` 仍在 import 它们 ⇒ `ImportError` ⇒ 上层捕获后整体禁用 | 逐定义追加恢复（**不整文件覆盖**，该文件含 vendor 分片逻辑） |

正确率 1/10 vs 2/10、耗时 870s vs 538s ⇒ **判定为不投入**。

## 六、答案必达与超时策略

**故障现场**：4 题端到端实测中，两题的最终答案是占位符
`[生成失败] 调用受限或模型拒绝回答`。根因不是超时本身，
而是**超时之后占位符被四层放行**（占位候选 → 兜底判据 → 拒绝正则 → 出口校验）。

**两侧修复**：

| 侧 | 改动 |
|---|---|
| 输入侧（超时） | 读超时 180s → **120s**；**超时类故障默认不再重试**（实测 5/5 全败，纯亏 timeout 秒）。单次故障成本从 365s 降到 120s |
| 输出侧（兜底） | 新增 `_subgoal_answer_candidate()` 做**形态校验**：`\boxed{}` 取值，或剥掉提示前缀后 ≤60 字符的无换行短值，且必须同时通过拒绝语内容校验 |

另修掉一个**我自己引入的回归**：rescue 失败时不替换 `final_response`；
以及「`无解` 被误判为没有答案」。

**残留风险（如实记录）**：单题上限在**两次调用之间**判定、无法中断在途调用，
理论最坏 `1100 + 120 = 1220s` 仍可能越过 1200s 硬墙。缓解手段是
`critical_tail_seconds`（默认 120s）。

## 七、选择题批次（B0 / B1 / B2）

### 7.1 三层结构

针对选择题建立「**基准子目标 + 逐项判定 + 分型路由**（单选 / 多选 / 求值）」，
替代此前把选项当普通文本处理的路径。

### 7.2 两个真 bug

| bug | 表现 | 根因 |
|---|---|---|
| 差分检测**从不执行** | `6_format` 阶段恒跳过 | `gen_time_up()` 误用 ⇒ 护栏**永久生效** |
| 多数投票**票数口径错** | 任何候选分布都被判为平票 | 用 `len(answers)` 当票数 |

### 7.3 结果（诚实标注）

- 逐项判定**确实生效**（三项证据），但没有救回 096（`ACD×3 > D×2`，
  **多数票本身就是错的**）；
- 剩余 8 道选择题最终结论：4 个错题**全部是「多解 / 歧义」题** ——
  这类题不是「机制没触发」，而是**题目本身有多个合法答案**；
- 三层结构有一处副作用（基准共享）需持续观察；
- **差分检测至今未取得正面验证**（构造数据 4 用例全通过，但真实题上未观察到收益）。

### 9.3 ⚠ 新的运维风险

```text
         Further push might be rejected.
```

建议在 gitcode 项目设置 → 项目管理 → **仓库压缩（Compact）**。
⚠ 本机侧**绝不做** `git gc --prune=now`（既有铁律）。

### 9.4 两条重要的工程教训（本阶段新增）

1. **改 Windows 上带 CRLF 的文件必须二进制读写**：Python 文本模式 `read()`
   在**读取阶段**就把 `\r\n` 归一成 `\n`，`open(..., newline="")` 只在写出阶段生效、
   救不回来 —— 实测一次静默剥掉 1272 个 CR。
2. **副本漂移检查必须全量 + 字节级**：只比「你以为改过的那几个文件」必然漏报；
   只有扫全部 `.py/.sh` 并用 `rb` 比对，才查出真实的 6 个文件漂移。
