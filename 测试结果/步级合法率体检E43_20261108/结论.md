# E43 步级合法率体检 —— 把「49% 的 goal state 不存在」查到底

**日期**：2026-11-08 · **性质**：离线、确定性、零 LLM 配额、无随机性 · **生产代码改动：0**

---

## 1. 起因与结论一句话

E42 顺带发现：三臂去重后的 283 个 goal state 里 139 个（49.1%）**前缀本身在 Lean 里编译不过**。
本轮按**步**（不是按去重点）把 354 步全部离线重编译，结论：

> **这个洞是 `测试结果/L2逐步探针_20261107/l2_step_probe.py::compile_check` 独有的，
> 生产侧没有。49% 是探针协议的产物，不是智能体的能力数据。**

机制：探针的判据顺序是

```python
if rc == 0 and not has_sorry and not ANY_ERR:   -> CLOSED
if UNSOLVED.search(raw):                        -> UNSOLVED   # ★ 命中即 return
err_lines = ...                                 -> ERROR
```

而 Lean 在**致命错误之后会做错误恢复，仍输出 `unsolved goals`**。所以只要出现
`unknown constant` / `Type mismatch` / 逗号分隔 tactic / 缩进散架，探针照样返回
`UNSOLVED`，把非法步 `tactics.append(tactic)` 进前缀，下一步继续在塌掉的地基上问模型。
另有同源缺陷：`ANY_ERR = r":\d+:\d+: error:"` 与 `UNSOLVED` 正则都只认 `error: `，
漏掉 Lean 4.31 的 `error(lean.unknownIdentifier): ` 格式（本轮日志里共 151 条）。

## 2. 生产侧核查（决定这条结论能不能外推）

| 位置 | 判据 | 是否有洞 |
|---|---|---|
| `replay_lean_close.py::classify` | docstring 明写「判据不是有没有 unsolved goals，而是有没有**别的** error 行」；2026-11-04 已因此修过 12 条误放 | 无 |
| `tools/agent_toolkit/lean_check.py` | `res.ok` 时仍取 `items_err`，任何 error → `proof_failed` / `statement_error` | 无 |
| `tools/lean_local/lean_bridge__mcp.py` | `errors = [severity=="error"]` → `if errors: ok=False` | 无 |

且生产是「整段编译 + 诊断分类」，**不是逐步交互形态**，根本没有「把非法步 append 进前缀」这条路径。
⇒ E42/E43 量到的 49% **不能外推为「智能体写出 49% 非法 Lean」**；这是本轮对 E42 结论的收紧。
模型形式化能力的干净量应取「**合法前缀条件下，本步 tactic 引入硬错误 27.6%**」（见下）。

## 3. 协议

- 三臂（`b_fix` / `base2` / `rej`）共 54 条轨迹、**354 步**，其中 329 步真的编译过
  （25 步是 EMPTY / BANNED，探针提前 return，没生成代码）。
- `build_body` 与 v3 探针 `build_code` **逐字一致**（含 `SORRY_TAIL` 替换与缩进规则），
  不关 `autoImplicit`（E39 只改门 A 编译，主编译口径不变）。
- 三个文件、同一批步，互为**单变量对照**：

  | 文件 | 内容 |
  |---|---|
  | `S_full.lean` | sig + 前缀 + 本步 tactic（探针当时编译的东西） |
  | `S_prefix.lean` | sig + 前缀（探针在每步开头编译的东西） |
  | `S_full_ind.lean` | `S_full` 但多行 tactic 每行补 2 空格（只改缩进） |

- 共 **987 条 example**；每条后 `#eval "MARK_<idx>"` 哨兵；编译用
  `lean -DmaxErrors=10000`（文件内 `set_option maxErrors N` 在 Lean 4.31 无效）。
- 服务器串行 **59 秒**；三份日志各 329 个哨兵全出现、**0 条未归属诊断**。
- 严格分类：`INVALID`（哨兵缺）/ `HARD_ERROR`（存在非 unsolved-goals 的 error，
  两种 error 格式都认）/ `SORRY` / `CLOSED`（零 error 零 sorry）/ `OPEN`（只剩 unsolved goals）。

## 4. 结果

### 4.1 核心对照：探针 verify × 严格判据

| probe \ strict | OPEN | CLOSED | HARD_ERROR |
|---|---|---|---|
| `CLOSED` (5) | 0 | **5** | 0 |
| `ERROR` (8) | 0 | 0 | **8** |
| `UNSOLVED` (316) | **121** | 0 | **195** |

**探针记为 UNSOLVED 的 316 步里，195 步（61.7%）严格判为硬错误。**
`CLOSED` / `ERROR` 两行完全对齐 ⇒ 分歧只出在 UNSOLVED 这一支，与机制预测一致。

### 4.2 前缀归因与真实合法步率

| 指标 | 数字 |
|---|---|
| 前缀本身非法（`S_prefix` = HARD_ERROR） | **155 / 329 = 47.1%** |
| 前缀合法 | 174 / 329 |
| 前缀合法条件下，本步 tactic 引入硬错误 | **48 / 174 = 27.6%** |
| 严格合法步率（全体 329 步） | **126 / 329 = 38.3%** |
| 探针口径合法步率（全体） | 316 / 329 = 96.0% |
| 严格合法步率（仅前缀合法的 174 步） | **126 / 174 = 72.4%** |

47.1%（按步）与 E42 的 49.1%（按去重点）互相印证，不是两次不同的现象。

### 4.3 分层

- **按臂**：`b_fix` 70.6% / `base2` 73.0% / `rej` 73.3% —— 三臂几乎一致，
  说明这是**系统性判据问题**，不是某一臂的随机波动。
- **按步序**：step1 **88.9%** → step2 73.3% → step4 48.0% → step6 40.0%。
  越往后越烂，符合「非法前缀不断累积」的机制（不是模型越写越差）。
- **按题**（18 个 tag）：min 0% / 中位 75.0% / max 100%。

### 4.4 修多行缩进（单变量）

| 项 | 数字 |
|---|---|
| 多行 tactic 步 | 34 |
| 修缩进救回 | 2（5.9%） |
| 全体 203 个 HARD_ERROR 步里救回 | **2（1.0%）** |
| 反而变坏 | 0 |

⇒ 与 E42 的 6/144（4.2%）同方向：**缩进不是主因**。绝大多数硬错误来自模型写出的
`unknown constant`、`unexpected token ','`、`Type mismatch`、`omega could not prove` 等，
首错类型 top 12 已落盘在 `results.json`。

## 5. 人工抽验 + 独立复现（E42 吃过解析 bug，本轮不信任批量解析）

- 按**首条硬错误类型分桶（20 桶）分层抽 8 条翻案样本** + 4 条 OPEN 对照，
  清单与完整诊断见 `verify_samples.py` 输出 / `verify_map.json`。
- **8/8 翻案样本都是「至少 1 条真硬错误 + 1 条 `unsolved goals`」并存**：
  `Unknown constant Set.infinite_of_unbounded_forall_nat`、
  `unexpected token ','`、`Type mismatch`、`Tactic rewrite failed`、
  `failed to synthesize instance`、`introN failed` … 精确复现错误恢复骗局。
- **4/4 对照只有 `unsolved goals`**，无其他 error。
- 12 条各生成独立单文件在服务器重编译：**12/12 与批量解析逐条一致**
  （翻案样本诊断数 ≥2，对照恰好 1 条 `unsolved goals`）。见 `out/VERIFY.txt`。
- 严格判据单测 **15 passed**（含一条「回归锚」：把旧判据顺序原样复刻，
  断言它在该样本上确实返回 `UNSOLVED`，防止有人再把顺序换回去）。

## 6. 修复交付（史料不回改）

**不修改** 11-07 / 11-08 任何历史探针脚本——它们是可复现证据。
新交付 `compile_check_strict.py`：

- 判据顺序改为 `ERROR > UNSOLVED > CLOSED`；`CLOSED` 必须 rc==0 + 零 error + 零 sorry；
  诊断正则同时兼容 `error: ` 与 `error(lean.xxx): `。
- **状态集合不变**（`{CLOSED, UNSOLVED, ERROR, TIMEOUT}`）：硬错误归到 `ERROR`
  而不是新增状态，否则旧 `run_one` 不认识新状态、会当 UNSOLVED 继续 append，反而更糟。
- `compile_check(code, tag, runner=None, ...)` 是 **drop-in**，返回形状与旧函数完全一致：
  后续探针改一行 import 即可，不用改 `run_one` 任何一行。
- 纯函数、零项目依赖，`runner` 可注入 ⇒ 可单测。

## 7. 不宣称 / 边界

- 本轮是**探针轨迹的离线性状**，不能推回生产智能体行为（见 §2）。
- 「严格合法」只表示**代码在 Lean 里合法且未闭合**，≠ 语义忠实、≠ 非平凡、≠ 可证；
  门 A 的 `False` 骨架盲区仍在（E40）。
- 不是效果量，也没有做任何 A/B：n=18 仍在 E41 量出的噪声底内。
- 48/174 = 27.6% 是「本步引入硬错误」的观测比例，不是模型能力上限的估计；
  它依赖三臂随机前缀，且 155 个坏前缀下的步**从未被测**。
- 未改生产代码、未动 `POLICY` 101 项、未加任何开关。
- 全量回归 `pytest tests tools -q`：**tests=2597 / failures=1 / errors=0 / skipped=7**，
  唯一失败恒为环境性 `test_compile_fail_returns_feedback`（wsl.exe 被安全策略拦）。
  与 E40 那次的 junit 报告**去掉耗时/时间戳后逐字节相同**（用例集合差集 0）
  ⇒ 本轮产物没有污染生产测试套件。
  （注：DOM 里 `<testcase>` 元素为 2541 个，与 `tests=2597` 的差是 pytest 自身
  计数口径，两次完全一致，不是用例丢失。）
