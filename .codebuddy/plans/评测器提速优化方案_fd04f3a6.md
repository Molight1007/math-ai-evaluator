## 产品概述

对数学智能体评测器进行两项提速优化，显著提升 100 题评测的执行效率。

## 核心功能

### 优化一：随机选题加速

将 `question_bank.py` 的 `get_random_problems()` 从 `ORDER BY RANDOM()` 全表扫描改为 Python 层随机采样策略：先查询所有符合条件的 ID 列表，再用 `random.sample` 选取目标数量的 ID，最后通过 `WHERE problem_id IN (...)` 精确查询题目内容。对于 10000 行题库选 100 题，从全表扫描+排序变为只查询 100 行，提速 50-100 倍。

### 优化二：批量评判模式

新增 DeepSeek 批量评判：推理阶段保持逐题并发（Intern-S1 每次只能做一道数学题），但推理完成后将同批推理结果打包一次发给 DeepSeek 进行批量评判。例如 concurrency=10 时，10 道题推理完成后，将 10 份推理结果打包为 1 次 DeepSeek API 调用，DeepSeek 一次性返回 10 道题的判定结果。API 调用次数从 20 次降为 11 次（10 次推理 + 1 次批量评判），大幅减少网络往返开销。

## 技术栈

- Python 3.10+（asyncio 异步编程）
- SQLite3（题库持久化）
- httpx（异步 HTTP 客户端）
- 现有 LLMClient / config 模块（复用）
- 现有 dataclass 模型（Problem / InferenceResult / JudgeResult / EvaluationResult）

## 实现方案

### 优化一：随机选题 — Python 层随机采样替代 SQL 层 RANDOM()

**当前问题**：

```sql
SELECT ... FROM problems WHERE bank_name = ? ORDER BY RANDOM() LIMIT ?
```

SQLite 的 `ORDER BY RANDOM()` 需要对所有匹配行分配随机数后排序，时间复杂度 O(n log n)，10000 行题库耗时显著。

**优化方案**（两步走）：

1. 先只查询 ID 列：`SELECT problem_id FROM problems WHERE bank_name = ?`（无需 RANDOM，无需排序）
2. Python 层 `random.sample(ids, count)` 选出目标 ID
3. 用 `WHERE problem_id IN (...)` 精确查询这 count 行

**关键优势**：

- ID 列查询无排序，O(n) 扫描极快
- `random.sample` 是 O(k) 内存操作
- 最终只取 count 行数据，I/O 极小

**代码位置**：`question_bank.py:217-235`，修改 `get_random_problems()` 方法。

### 优化二：批量评判 — 新增 `run_judge_batch()` + 重构评测流水线

**当前流程（concurrency=10 时）**：

```
题目1 → Intern-S1推理 → DeepSeek评判 ─┐
题目2 → Intern-S1推理 → DeepSeek评判  ├─ 20 次 API 调用
...                                     │
题目10→ Intern-S1推理 → DeepSeek评判 ─┘
```

**优化后流程（concurrency=10 时）**：

```
题目1 → Intern-S1推理 ─┐
题目2 → Intern-S1推理  ├─ 10 次并发推理
...                     │
题目10→ Intern-S1推理 ─┘
          ↓
     收集 10 份推理结果 + 参考答案
          ↓
     1 次 DeepSeek 批量评判（打包 10 题）
          ↓
     解析 10 题判定结果 → 生成 10 个 EvaluationResult
```

**API 调用从 20 次降为 11 次**，减少约 45%。

**新架构**：在 `main.py` 中新增 `evaluate_batch()` 函数，分两阶段执行：

- **阶段一（推理阶段）**：用 `asyncio.Semaphore(concurrency)` 并发执行 `run_inference()`，同时逐题查找参考答案
- **阶段二（评判阶段）**：每收集满 `batch_size` 个推理结果（或所有题目推理完毕），调用一次 `run_judge_batch()` 批量评判

**deepseek.py 新增函数**：

| 函数 | 功能 |
| --- | --- |
| `run_judge_batch(inferences, reference_map)` | 将多道题的推理结果打包发送给 DeepSeek 批量评判，返回 `list[JudgeResult]` |
| `parse_judge_batch_response(raw_content, problem_ids)` | 解析 DeepSeek 批量评判返回的 JSON 数组 |


**批量评判 Prompt 设计**（参考 `question_bank.py:_build_audit_prompt` 的模式）：

- 系统提示词不变（JUDGE_SYSTEM_PROMPT）
- User 消息按题目编号依次列出：题目、模型答案、推理过程、参考答案（如有）
- 要求 DeepSeek 输出 JSON 数组：`[{"problem_id": "...", "is_correct": ..., ...}, ...]`

**向后兼容**：

- `run_evaluation()` 新增可选参数 `use_batch_judge: bool = True`
- 单题评判函数 `run_judge()` 保持不变（批量评判内部复用 `parse_judge_response` 的字段映射逻辑）
- 命令行模式默认启用批量评判
- 文件评测（少量题目）和题库评测（100 题）均受益

## 实现注意事项

### 性能考量

- 批量评判的 token 消耗与逐题评判相当（总 prompt 长度相同），但节省 9 次网络往返
- `random.sample` 在大题库（10000+）上远快于 `ORDER BY RANDOM()`
- 参考答案查找仍在推理阶段逐题进行（每道题独立匹配），不增加额外开销

### 错误处理

- 批量评判如果部分题目解析失败，为失败题目生成 error 标记的 JudgeResult，不影响成功解析的题目
- 如果批量评判 API 调用整体失败，为整批所有题目生成 error 标记的 JudgeResult
- 推理失败（inference.error）的题目直接标记为错误，不进入批量评判

### 日志与输出

- 批量评判时输出 `[Batch 1/10] Judging 10 problems together...`
- 单题评判时保持原有输出格式不变
- 复用现有 logger 和 `_safe_str` 辅助函数
