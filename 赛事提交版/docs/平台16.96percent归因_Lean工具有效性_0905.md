# 平台评测 16.96% 归因：Lean / DAG / 子目标到底有没有提高正确率

> 分析对象：`eval_log_46d0268f152d4a58a9b5bbe5c330b919.log`（gitcode commit **3569d53**）
> 结果：16.96%（19 对 / 37 错 / **56 invalid**），agent 阶段 10h55m，valid_accuracy 33.9%
> 日期：2026-09-05

## TL;DR（结论先行）

1. **这个 16.96% 不能证明"Lean/DAG/子目标没提高正确率"**——平台**没有 Lean 环境**，本次运行里
   Lean 工具全程 `unknown` 降级（不剪枝、不拦错、不验证），等于只付时间不办事；56 题压根没跑到
   "出最终答案"那一步就被 1200s/题 时间墙切掉（invalid），不是答错。
2. **在"能答完"的题上，工具确实提高了正确率**：本地全量 45 题基准 22.2% → Lean 时代最佳组合
   35.6%（+13.4pp）；平台"答完的题"答对率 23.2%（c2dd61d 全量）→ 33.9%（3569d53）。
3. **平台砸分唯一元凶 = invalid（完成率），不是正确率引擎**：2534334（invalid 64）与 3569d53
   （invalid 56）连续两轮 ~50% 题无答案，把 33% 的 valid_accuracy 稀释成 16-17% 总分。
4. Lean 对平台的价值定位本来就是**本地证据链 + 材料（40%）**；平台分靠"AI 判分 × 答完率"。
   Lean 时代 pipeline 变重（Step2 无条件 + value_attack + collab + 子目标+merge + token 放开 +
   deep 6.5 不放过到 1200s），答完率被牺牲 → 总分反而低于无 Lean 时代的轻量版 c2dd61d（23.21%）。

## 三、56 invalid 的机制链（哪些是证据、哪些是推断）

**为什么"没有 Lean"（9/5 晚代码实证，修正早期笼统表述）**：不是"平台不允许"，而是**仓库里根本没有 lean/lake 可执行文件**——
- `.gitignore` 明确排除 `deploy/lean-cache/`、`deploy/*.zip`、`deploy/*.tar.gz`、`lean下载版/` → 离线安装包 `deploy/lean-4.31.0-linux.zip` 从未入仓；
- 入仓的只有 `deploy/mathlib-olean/`（920 个 .olean × 文件类型 ≈ 9200 文件/695MB，Mathlib 依赖闭包 = "数学书"），没有 lean 编译器 = "阅读器"；
- `detect_lean_environment` 探测流程：`which(lean)` 失败 → 自动跑 `bash deploy/setup_lean.sh --offline` → 在线(elan)无外网失败、离线缺 zip 失败 → `available=False`（缓存）→ preverify 编译 / lean_filter 剪枝 / lean_gate 硬门禁 **全部 unknown 降级放行**（代码确认，安全降级不崩）；
- 平台日志佐证：环境检查只有 pip/sympy，无任何 lean/lake 安装输出；Updating files 9324 = 恰好 9200 闭包文件 + 代码文件。
- 本地能跑 Lean，是因为 lean 本体在仓库外（`D:\lean下载版` / `D:/mathlib4-last_bump_for_v4.31.0` 工程 + PATH），从未进 git。
- LeanSearch（use_leansearch=True）无外网不可用 → 全局前提检索实际为 0

推断链（标注强/弱推断）：
1. 【代码事实】平台无 Lean + 无外网 → 客观剪枝失效，错误候选只能靠 LLM 投票/对抗/revise 淘汰。
2. 【强推断】pipeline 比 c2dd61d 重：Step2 无条件 self-improve、value_attack、collab、子目标+merge、
   deep 3 候选 × 3 票、deep 6.5"不放过到 1200s"；且 token 放开后 Intern-S2（推理模型）单次调用
   100-200s+ → 单题 LLM 链普遍逼近 1200s 墙。
3. 【强推断】整批被墙占满：112 题 × 1200s ÷ 并发 3 ≈ 12.4h 上限 ≈ 实测 10h55m → 每题几乎都跑到
   墙边；56 题在产出最终答案前被切 → invalid（历史归因口径：被窗口切掉无最终答案）。
4. 【弱推断】3569d53 加了 6.5 档位封顶但总时长几乎不变 → 说明时间主 sink 不在 6.5 重做循环，
   而在更早的 LLM 主链（preverify+subgoal+solve+投票）。砍 preverify 省下的时间（sketch audit 关）
   又被子目标/求解吃掉（与 9/4 mcp 轮 6/18 观察同型）。

> 诚实声明：invalid=56 的**逐题**归因无法从本 log 验证（平台只回传汇总，无每题明细）；
> 上述为基于代码事实 + 耗时/token 证据的强推断，与 9/4 对 2534334 的归因一致。

## 五、必须直说的偏差

- 平台 valid_acc 33.9%（3569d53）**不能**直接与 c2dd61d 的 23.2% 比大小：时间墙下"先跑完的"
  偏向简单/短题 → 答完集不是随机样本，valid_acc 被系统性高估。诚实的说法是：
  **"答完的题正确率看起来更高，但无法据此断言引擎变强了多少"。**
- 本地 35.6%（45 题全量答完、无墙）才是 Lean 时代工具增益的**干净证据**。
