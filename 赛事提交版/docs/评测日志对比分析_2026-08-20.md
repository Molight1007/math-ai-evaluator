## 三、根因分析：为什么 08-19 分数下降？

### 直接原因：每题 LLM 探索量减半

请求数 2203 → 1160（-47%），总 token 同样减半。也就是说 **08-19 版本每道题平均只做了约一半的 LLM 推理/验证工作**，深度的探索被砍掉了，正确率随之下滑。

### 代码级证据

对 `93075df`（08-17 评测）与 `0d2c4ac`（08-19 评测）做代码对比：

**1. v2.5（08-17，高分组）带完整"难题路由 + 时间管理 + 深度通道"**
- `enable_difficulty_router=True`、`enable_llm_difficulty=True`，按难度分三档（fast/standard/deep）；
- **deep 档（难题）**：`tier_sample_times={fast:1, standard:2, deep:4}`（4 个候选）、每候选多次投票、`deep_use_sub_goal=True`（子目标分解）、`deep_revise_rounds=1`（revise 回环）、`deep_use_playoff=True`（复算决选）；
- 因此难题平均消耗 ~20 次 LLM 调用。

**2. LeanBridge 版（08-19，低分组）回归"简化版流水线"**
- orchestrator 中 **不再引用 `DifficultyRouter` / `PaperPacer` / tier 系统**（`agent/` 目录中相关文件消失，`user_agent.py` 中 `enable_difficulty_router`、`tier_*`、`deep_*` 字段全部移除）；
- 流水线固定为：分类 → 3 候选（`policy_sample_times=3`）→ 每候选 2 投票 → 可选 1 轮 revise，设计目标"每题 LLM 调用控制在 7 次以内"；
- 每题平均 ~10.4 次调用。

### 排除项：Lean 硬验证并非下降原因

- `enable_lean_verify` 默认 `False`（代码注释：保守兼容）；
- 评测环境只装了 gcc / z3，**没有 Lean/elan 工具链**，即便开启也无法运行本地 Lean 验证；
- 结论：本次 08-19 评测中 LeanBridge 基本未生效，分数下降与 Lean 本身无关。

## 四、建议

1. **提交/评测基线应恢复到 v2.5（`93075df`）**：它是当前最高分版本（20.54%），带完整难题路由与深度通道。
2. **LeanBridge 应在 v2.5 完整版基础上合并**，而不是在简化版上开发——把 Lean 验证作为 deep 档难题通道的"额外硬验证层"，同时保留多候选/多投票/revise/playoff。
3. **Lean 硬验证要真正生效需在评测环境预装 Lean 工具链**（当前环境仅 gcc/z3），否则 `enable_lean_verify` 开了也是空转。
4. **注意 git 线混乱**：gitcode 端仓库被 force-push 重建（`6ccc208` 为孤儿根），建议重新梳理：以本地 v2.5 线为基准，将 LeanBridge 改动 cherry-pick/合并过去后重新推送，避免再次评测到错误基线。
