# L2 逐步交互探针（2026-11-07）

零配额之外的模型侧小样本探针，**不是评测、不产效果量**，只用来看「L2 形态通不通、卡在哪一层」。

## 结论摘要

| 配置 | A 组（10 条一行可闭合） | B 组（18 条 E37 STATABLE 真题） |
|---|---|---|
| 一次性整段序列（v2 口径，仅作对照） | 8/10 | 2/18 |
| 逐步循环，无语法表 | 7/10 | **0/18** |
| 逐步循环 + Lean 4 语法对照表 | — | **2/18** |
| 逐步循环 + 语法表 + 编译错误反馈（2 轮） | 9/10 | **2/18** |
| 逐步循环 + 语法表 + 反馈 + **Mathlib 源码检索**（主动 `SEARCH:` + 错误自动检索） | 9/10 | **1/18**（q10 退化，n=1 无法判因果） |
| 纯检索（`omega`/`norm_num`/`simp`/`positivity`/`ring`/`exact?`/`apply?` 依次试，不调 LLM） | — | **1/18**（就是 q21） |

**五组都收敛在 1-2/18 ⇒ 瓶颈不在协议、不在检索，在模型。**

Mathlib 源码检索本轮已**真正装好并验证可用**（见第 4 节），但模型 **0 次主动调用**，
且「忘记引理名」类错误在 B 组出现 **0 次** ⇒ 检索的**理论上限是 0**。

## 1. 协议缺陷（已修）

一次性「给出能闭合它的 tactic 序列」有两个假阴性：

- `s07`：`use 7` 已闭合 `∃ n, n = 7`，模型多写一个 `rfl` ⇒ `No goals to be solved` ⇒ 判 FAIL。
- `q20`：`apply Nat.Prime.dvd_factorial hq` 已闭合，多写的 `exact ...` 报同样错。

逐步循环（每步编译取新 goal，无 goal 即停）从协议上消除这类假阴性。

## 2. Lean 4 语法对照表（有效）

修复前 B 组 `unknown tactic` 4 条（q01/q05/q24/q26），全部是 **Lean 3 写法**：

```
cases h with x h      → Lean 4: obtain ⟨x, h⟩ := h
cases ho with k hk    → Lean 4: obtain ⟨k, hk⟩ := ho
refl                  → Lean 4: rfl
existsi 7             → Lean 4: use 7
induction n with k ih → Lean 4: induction n with | zero => ... | succ k ih => ...
```

加对照表后 `unknown tactic` **清零**，q05/q06 从 COMPILE_ERROR 推进到「走完 10 步」，q10/q21 直接跑通。

## 3. 编译错误反馈（对闭合率 0 贡献）

B 组带 2 轮反馈：触发 **9 个 step / 14 轮**，其中只有 3 轮把 ERROR 修成 UNSOLVED（语法层），
其余 11 轮是「换一个错的」：

```
q04  rw 失败 → rfl → rw [h]                 全都是瞎换
q26  omega 失败 → linarith → by_cases → contradiction → exact   全都不对
q02  rw 失败 → ring_nf → ring               全都不对
```

且 q10/q21 两条 PASS 在「只有语法表」时就已通过，**修复循环没有新增任何一条 PASS**。
成本约 +50%（每步多 1-2 次 LLM + 编译）。

与队友 `1de9a01`（编译反馈迭代）对照：他们的成本墙（单条 3 轮 >30 分钟）**在逐步形态下不存在**
（B 组 18 条总计 ~20 分钟，单条最长 86 秒），但**收益同样为 0** —— 编译反馈能修 API 名，
修不了证明策略。

## 4. 引理检索：装好之后仍然无收益（负结果）

### 4.1 先把环境补齐（本轮实际成果）

原先的「物理不可用」有**两个洞**，本轮都补上了：

1. **没有 `rg`** → `sudo apt-get install ripgrep`（14.1.0，`/usr/bin/rg`）
2. **没有 Mathlib 源码** → 按 `lean-toolchain` 反查 tag 精确对齐：

```
deploy/mathlib-olean/lean-toolchain  =  leanprover/lean4:v4.31.0
git ls-remote --tags ...             →  refs/tags/v4.31.0 = fabf563a7c95a166b8d7b6efca11c8b4dc9d911f
下载: GitHub 直连 8 分钟未完（限速）→ 改 ghfast.top 镜像, 22.8MB / ~12s
安装: 只取 Mathlib/ 子目录 → deploy/mathlib-olean/Mathlib/（不覆盖壳项目的 lakefile.toml / lake-manifest.json）
规模: 8169 个 .lean, 112MB；目录总计 5.7G
版本记录: deploy/mathlib-olean/MATHLIB_SRC_VERSION.txt
```

验证（`op=local_search`）：

```
mul_div_cancel          → 5 条，含 mul_div_cancel (theorem, Mathlib/Algebra/Group/Basic.lean)
dvd_factorial           → 2 条，含 Nat.Prime.dvd_factorial (Mathlib/Data/Nat/Prime/Factorial.lean)
Nat.Prime.dvd_factorial → 精确命中 1 条
```

加源码后原编译链不受影响（`Nat.mul_div_cancel` 报「类型不匹配」而非「未知标识符」⇒ 引理被正常识别）。

★ **olean 覆盖洞（必须设闸）**：源码 **8169** 个模块，本机 olean **7589** 个 ⇒
**633 个模块「有源码、无 olean」**，集中在 `Algebra/Category`（范畴论/层论）。
检索若命中这些模块，会给出模型引用了也编不过的名字 —— **比不检索更糟**。
探针已加 `_has_olean()` 闸门：命中项的 `.olean` 不存在就丢弃，并打印 `[search] kept x/y`。
实测 `sheafification`：命中 5 条 → 过滤掉 1 条（`Algebra/Category/.../Sheafification` 缺 olean），
保留 `CategoryTheory/Sites/Sheafification` 的 4 条。

注：`index: unavailable` 仍会出现，但它的含义是**没有 LSP 符号索引**；`sources_searched: ["source_text"]`
说明源码检索在工作 —— 按工具自带说明，只要有 source_text 结果，空结果才需要 index=consulted 才算证据。

### 4.2 装上之后：模型不用它

探针加了两条检索通道：

- **主动**：模型不确定时输出 `SEARCH: <关键词>`，检索结果回填下一轮 prompt，不计步数（上限 5 次/题）
- **自动**：编译错误含 `unknown identifier/constant` 时，自动检索该名字并注入修复 prompt

B 组实测：

```
主动检索触发：0 次
自动检索触发：0 次（因为该错误一次都没出现）
结果：1/18（唯一 PASS 是 q21）
```

### 4.3 为什么注定无用：上限是 0

对无检索版 18 条的全部错误文本分类：

| 错误性质 | 次数 |
|---|---|
| 策略无效（`made no progress` / `could not prove` / `tactic failed`） | 19 |
| 语法 | 2 |
| 其它 | 2 |
| **忘记引理名（`unknown identifier` / `unknown constant`）** | **0** |

**检索能治的病，这个模型在 B 组上一次都没犯。** 它的错误是「策略不成立」，不是「名字记错」。
这也解释了模型为何 0 次主动检索：它的自我判断是对的，它不缺名字。

★ **订正**：此前口头判断「q04 报 `Unknown identifier mul_div_cancel'`，属第③层缺口、检索能救」——
那条错误属于**早期一次性整段序列**版本（`l2_probe2_all.json`），逐步版 q04 是 `rw [h] at h` /
`obtain ⟨h⟩ := h` 这类无意义操作，属「策略无效」。**两版 `unknown identifier` 均为 0 条**，原判断不成立。

### 4.4 q10 的退化不能归因于检索

无检索版 q10 `CLOSED`，检索版 `EMPTY`。查 trace：检索版 step1 把整段证明写成**逗号串联的一行**
（`have h1 := ..., have h2 := ..., linarith`），step2 自认「已闭合，无需进一步步骤」⇒ EMPTY。
这是「多步合并 + 自我误判」，与 `SEARCH:` 协议无关。

但 n=1、且已证实温度 0 也不收敛 ⇒ **既不能判为噪声，也不能判为副作用，只能说无法判定**。

### 4.5 之前那版纯检索（Lean 内置 tactic）同样 0 收益

`exact?` / `apply?` 在 `import Mathlib.Tactic` 下可用，对简单目标确实闭合，但 B 组 18 条依次试
7 个 tactic 只解 1 条（q21，模型本来就能过），**净增 0**。`apply?` 在 q20 上给出方向
（`Nat.dvd_sub`，剩 3 个子目标）但不闭合。B 组都是多步证明，不存在「一个引理搞定」的解。

### 4.6 本轮自我纠错（第 4 次）

第一次测 `apply?` 时写成 `lean x.lean 2>&1 | head -20; echo rc=$?` ⇒ **`$?` 取的是 `head` 的退出码**，
误得 `rc=0` 判定「apply? 能闭合 q20」。重测时把 lean 输出重定向到 `/dev/null` 才拿到真 rc。
**教训：测量退出码时绝不能把命令放进管道尾部。**

## 5. 失败模式（B 组）

| stop | 语法表 + 反馈（无检索） | + Mathlib 检索 |
|---|---|---|
| CLOSED | 2（q10 / q21） | 1（q21） |
| EMPTY（主动放弃） | 8 | 5 |
| MAX_STEPS（打转） | 2 | **8** |
| COMPILE_ERROR | 5 | 4 |
| BANNED（写 sorry） | 1 | 0 |

加入检索后 **MAX_STEPS 从 2 涨到 8**：模型不再卡在语法和类型上，能持续写出可编译的 tactic，
但 10 步之内推不动目标。这比「编译错误」更明确地指向**证明策略**这一层，而不是 API 名称层。

典型错误（全部是类型/策略层，无一条语法、无一条未知标识符）：

```
q08  numerals are data in Lean, but the expected type is a proposition
q11  Application type mismatch
q15  Function expected at
q26  omega could not prove the goal
q20  `simp` made no progress
q01  Tactic `contradiction` failed
```

`q08` 把数字 `2` 当命题 —— 把 Lean 当自然语言写，与 E37「命题形式化质量比证明能力更靠上游」同源。

## 6. 不宣称

- 不宣称 L2 有效或无效；1-2/18 都是 **n=18 单次采样**，无区间估计，且已证实温度 0 也不收敛。
- 不宣称「1/18 vs 2/18」是检索造成的效果量；q10 退化 n=1，无法判因果（见 4.4）。
- 不宣称「检索无用」是普适结论。准确表述：**在本模型、本题单上，`unknown identifier` 出现 0 次，
  检索没有适用对象**；换一个爱记错名字的模型，结论可能不同。
- 不宣称「语法表 +2」是效果量；A 组 7→9 的提升本次**修复循环一次未触发**，归因在语法表，但未做严格单变量对照。
- 不宣称模型能力边界；只陈述「在本配置、本题单上 ≤2/18，且失败集中在策略层」。
- `q13` 的 brief 曾显示成 linter `Note:`（末行），已核实为真 error，非误杀；探针已改为取首条 `error:` 行。
