# MathPilot 逻辑缺陷修改计划

> 依据：2026-09-16 ~ 09-17 五轮评测的实测数据（见《MathPilot 全量测试数据汇总》）。
> 范围：**已诊断清楚但尚未修改**的问题。这些**不是代码 bug**（代码按写法运行正常），
> 而是**逻辑设计错误**或**可观测性缺口** —— 需要改判据、改结构或改注入方式。
> 每项给出：问题 → 根因（含代码位置）→ 修改方案 → 验证方式 → 风险。

## 二、逐项修改方案

### 问题 1 · 子目标链锁定错误答案（最高优先级）

**根因**

规划阶段默认"本题只有一个答案"，第一步就断言 `a_0 = 0`（错误），
后续子目标全部建立在它之上。`003` 的 `blueprint_merge` 也写
`n4 yields a_2025=2025 as sole value`，说明**蓝图与子目标两层同时锁定**。

关键观察：`subgoal_stats` 显示 `dep_free: 1` —— **整条链只有一个无依赖入口**，
没有任何并行的独立验证分支。一旦入口错，全链皆错。

**修改方案**

1. **首个子目标不做"断言式证明"，改为"候选枚举"**
   把 `Prove a_0 = 0 by contradiction ...` 改为
   `Enumerate all possible values of a_0 consistent with the constraint`，
   要求**列出所有可能取值的候选集**并给出各自成立/排除的理由。
   这样第一步就不锁定唯一值。
2. **为"求所有"题增加一条并行分支**
   在依赖图上，除主链外挂一条**不依赖主链任何结论**的独立求解子目标
   （`depends_on: []`），用不同方法独立求一次答案。
   主链与独立分支的结论**不一致时**，触发定向复核（而非直接采信主链）。
3. **merge 阶段要求显式对照**
   `merge_strategy` 中强制说明"主链结论 / 独立分支结论是否一致；若不一致如何处理"。

**验证方式**

- 埋点：`subgoal_stats.dep_free` 应 ≥ 2（主链入口 + 独立分支）
- 对 003 重跑，观察 `blueprint_merge` 是否仍写 "sole value"
- 判据：候选答案中是否出现 `2026` 与 `2030` **两个值**

**风险**：增加 1 个独立求解分支 ⇒ 单题耗时上升（估计 +15~25%）。
可用 `max_subgoals` 控制总数，或仅在 `asks_all_values` 为真时启用。

### 问题 2 · 穷尽性检查被前序结论锚定

**根因**（`agent/sub_goal_solver.py:471-477`）

# ⚠ **必须依赖全部已有子目标**：执行期 `_format_dep_results`
# 只注入**直接依赖**的结果 —— 若只依赖最后一个，穷尽性检查就
# 看不到前面找到的任何解，而它的任务恰恰是"检查是否遗漏解族"。
"depends_on": [sg["id"] for sg in subgoals],

这是一个**真实的两难**：不注入 ⇒ 看不到前序解、无法判断遗漏；
注入 ⇒ **被前序结论锚定**。当前选择了全量注入，实测结果是**只复述、不质疑**。

**修改方案**

保留注入（否则它无从对照），但**改变注入的语义框架**：

1. **把前序结论标注为"待检验假设"而非"已确立事实"**
   在注入文本前加一节：
   「以下结论**尚未经过完备性检验**，仅作为待验证假设列出。你的任务是找出它们**遗漏**了什么，
   不是确认它们正确。」
2. **强制输出结构化清单而非自由叙述**
   要求输出形如：
   - `解族清单: [常数解, 线性解, 周期解, 取整解, ...]`
   - `逐族判定: 族名 → 存在 / 不存在（依据）`
   - `结论: EXHAUSTIVE: yes|no`
   - `遗漏解族: [...]`（若 no）
3. **用 prefill 强制以 `解族清单:` 开头**（与深复核收敛调用同款手段），
   结构性保证它先列清单、再判定，**不能跳过列族直接给结论**。

**验证方式**

- 埋点新增 `exhaust_result`：解析出 `EXHAUSTIVE` 与解族数量
- 判据：003 重跑后 `exhaust_result.n_families ≥ 4`（当前实际为 0，因为它没列）

**风险**：低。仅改注入措辞与输出格式，不动依赖结构。

### 问题 3 · 穷尽性检查不可检测

**根因**

`subgoal_trace[i].result` 是**自由文本**。`003` 的穷尽性检查 `result` 是
`a_n = n \text{ for all } n \ge 0` —— 无法判断它是"列了所有解族后确认只有这一个"
还是"压根没列、直接把前序结论抄了一遍"。

**修改方案**

1. 按问题 2 的方案，要求输出**结构化字段**（`EXHAUSTIVE` / `解族数量` / `遗漏解族`）
2. 在 `_collect_diag` 中解析并写入 `exhaust_result`：
   `{"n_families": n, "verdict": "yes|no", "missed": [...]}`
3. **未按格式输出时判为"未完成检查"**（与深复核 `min_chars` 护栏同款思路），
   并在 diag 中标记 `exhaust_incomplete: true`

**验证方式**：重跑后 `diag.exhaust_result` 的 `n_families` 应 > 0。

**风险**：低。

### 问题 4 · LeanGate 对 003 七候选全放行（核心逻辑缺陷）

**根因**（`tools/lean_local/lean_bridge.py:2306-2371`）

`answer_valid` 的判定链是：**Lean 编译通过** → 两道守卫 → `answer_valid`。两道守卫对 003 都失效：

**守卫① `_cross_check_problem_numbers(problem, lean_code)`**
要求"验证代码必须引用题目关键数字（≥3 位数）"。但 **003 的题面里就有 `2025`（`a_{2025}`）**，
**而错误答案恰好也是 `2025`** ⇒ 任何提到 `2025` 的代码都通过 ⇒ **该检查在此题上完全空转**。

**守卫② `_verify_answer_by_system(reasoning, answer)`**
依赖"推理里带工具标记的算式"。而 `enable_calc_tool=False`（09-15 已关）
⇒ 推理里**永远没有 `<calc>` 标记** ⇒ 恒返回 `None` ⇒ **不拦截**。

⇒ 两个守卫全部失效 ⇒ 7/7 放行。

**修改方案**

1. **守卫①增加"排除答案自身的数字"**
   交叉核对时，把**候选答案里的数字**从"题目关键数字"集合中剔除：
   若验证代码引用的数字**全部来自答案本身**，则视为无区分度的自证 ⇒ 拒绝。
   （即：必须引用**题目约束**中的数字，而非答案里的数字。）
2. **守卫②改为不依赖 `<calc>` 标记**
   现在的实现要求推理中有工具标记 —— 这与"calc 已关"的现状矛盾。
   改为：**从最终答案与推理中直接提取数值等式**（不依赖标记），
   由系统构造 `(推导式) = (答案)` 并交 Lean 复算。
   若无法提取，**明确记录 `_sys = "no_expr"`**（而非静默 None），
   使"未拦截"这件事**可观测**。
3. **新增守卫③：答案形态合理性**
   对"求所有/全部"题，若最终答案是**单值**而题面要求多个值 ⇒ 判 `proof_invalid`
   并给出定向反馈。这一条直接针对 003（漏 `2030`）与 013 的失败型态。

**验证方式**

- 对 003 重跑：`lean_gate` 应不再全部 `answer_valid`；至少错误候选（2025）被拦
- 判据：`{"rejected": n>0}` 且被拒的是错答案

**风险**：**中**。守卫①收紧可能误杀"题目确实无区分度数字"的题。
建议：**先加埋点观测**（记录每道守卫的判定与依据），跑一轮确认无大规模误杀后再启用拦截。

### 问题 5 · Lean 验证 230s 零产出（连带问题）

**根因**

`3.6_audit_filter` 阶段**同时包含 LeanGate 与 AuditGate**。
实测 `3.6_audit_filter = 229.9s` ≈ `lean_mcp seconds = 239.4s`
⇒ **这 230 秒几乎全是 Lean 验证**。而 Lean 的判定（7/7 放行）无效 ⇒ **纯浪费**。

**修改方案**

依附于问题 4 —— **判定有效性提升后，这 230s 才有价值**。
此外可做：

1. **候选级并行**：7 个候选串行编译 ⇒ 改为并行（注意内存，当前 `K=可用内存//4`）
2. **缓存**：同一题目内，**结论相同的候选**（如 5 个都是 `\boxed{2026}`）只需验证 1 次，
   其余复用结果。003 的 7 个候选里有 5 个是同一个答案 ⇒ 可省约 70% 时间。

**验证方式**：重跑后 `lean_mcp.seconds` 应显著下降（目标 < 100s）。

**风险**：低（缓存按"答案归一化后相同"为键，语义安全）。

### 问题 6 · AuditGate 对解答题结构性零输出

**根因**（`agent/audit_gate.py::audit_candidates`）

entry = {..., "verdict": "unknown"}     # 默认 unknown
if det.get("verdict") == "fail":   ...  # 只有确定性检查判 fail 才改
elif is_proof and use_rubric:      ...  # Level 2 rubric **只对证明题跑**

⇒ **非证明题（解答题）** 只能得到 `unknown`，除非 `DeterministicChecker` 判 fail。
两题都是解答题 ⇒ 6/6 全 `unknown`。

**修改方案**

1. **为解答题补一条客观判据**：沿用 `DeterministicChecker` 的数值代回，
   增加"答案与推理中数值等式是否自洽"的检查（0 LLM 成本）
2. **或明确标注为"不适用"**：把 `verdict: "unknown"` 改为 `verdict: "not_applicable"`，
   避免"unknown"看起来像"检查了但无法判定"

**验证方式**：重跑后 `audit_gate` 的 verdict 分布应有非 unknown 项，或明确为 n/a。

**风险**：低。

### 问题 7 · Lean 验证代码未落盘

**根因**

`lean_bridge.py:2339/2362/2370` 都执行了 `setattr(report, "lean_code", lean_code)`，
但 `_collect_diag` 落盘的 `lean_gate` 条目**只含** `id/verdict/lean_valid/degraded/error`，
**没有把 `lean_code` 带出来**。

**修改方案**

在 `lean_gate` 的 diag 条目中增加 `lean_code` 字段（建议截断至 2000 字符），
并同时记录**守卫判定依据**（`cross_check_ok` / `sys_verify` 的取值）。
落盘到单独文件 `results/lean_code_samples.jsonl` 以避免结果文件膨胀。

**验证方式**：重跑后能在样本文件中看到每道候选的 Lean 代码与守卫结果。

**风险**：低。这是**当前最该先做的一项** —— 没有它，问题 4 的修改无法验证。

### 问题 8 · 013 候选退化为推理散文（待查）

**现象**（E 轮 013 候选答案）

<parameter=que | \boxed{10} | \boxed{50} | subset sum逼近 1 | 看起来 d = 10 是候选 | \boxed{5}

**初判**：答案抽取环节把**推理过程**当成了答案 —— 出现了
`<parameter=...`（工具调用的参数残留）、`看起来 ... 是候选`（推测语气）这类明显非答案文本。

**待查方向**

1. 答案抽取的正则/LLM 抽取是否在"模型输出被截断"时退化为整段截取
2. `<parameter=` 残留说明**工具调用的 XML 片段泄漏进了正文** —— 需查工具循环的消息处理
3. 是否存在"抽取失败时回退到 reasoning 尾部"的兜底（该兜底会把散文当答案）

**修改方案**：待定位后制定。建议先补埋点记录"抽取前的原始响应"以便复现。

**风险**：待评估。
