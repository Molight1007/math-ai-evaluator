## 一、最重要的结论：判分器口径确实是主因

同一批 45 条历史作答，换用不同判分器得出两个差距悬殊的数字：

| 判分口径 | 正确率 | 说明 |
|---|---:|---|
| 严格判分器 `run_eval.answers_match` | **31.1%**（14/45） | 字符串 / 分数等价 / 浮点 1e-6 / SymPy 符号等价 |
| 宽松 LLM 判分（DeepSeek） | **46.7%**（21/45） | 本地历史报告采用，规则"结论对即判对" |
| 比赛平台（官方 Judger，112 题私有集） | **20.54%** | 不同题集，仅供参考 |

**差值 15.6pp 全部来自判分口径**，这基本解释了长期存疑的「本地 45% vs 比赛 20%」落差。

### 一个必须记取的教训
`answers_match` 的代码逻辑看起来是**四级宽松匹配**，容易让人只读代码就断言"判分器不是瓶颈"。
**必须跑数据**——跑完才发现它仍有系统性假阴性。只读代码得出的结论在这里是反的。

### 顺带修掉的判分器假阴性
严格判分器本身也漏判，修复后基线从 26.7% 回到 31.1%（捞回 2 条）：

| 问题 | 样例 |
|---|---|
| `\dfrac` / `\tfrac` / `\cfrac` 与 `\frac` 判为不等 | `$\dfrac{9\sqrt{3}}{16}$` vs `$\frac{9\sqrt{3}}{16}$` |
| `\boxed{}` 外壳未剥离 | `$\boxed{\frac{2617}{2618}}$` vs `$\frac{2617}{2618}$` |
| `\left` / `\right` 等排版命令未清理 | — |

> 修复位置：`run_eval.py::_clean_answer` / `_norm_candidate`

## 三、⚠️ 解读口径的前提

历史 `intern_answer` 由 **测试工具/ 本地评测路径**产出，该路径**自带抽取逻辑**
（`测试工具/intern_s1.py` 的 `_extract_boxed` / `_extract_tail_fallback`），
与比赛路径（`user_agent.py → agent/`，共用 `utils/extract.py`）**不是同一条代码路径**。

因此：
- `extract_failed` 的 3 条反映的是**本地评测路径**的问题，不能直接等同于比赛端丢分
- 但「判分口径落差」「答案未定型」两类结论**与路径无关**，对比赛端同样成立

后续若要测比赛端真实基线，需跑 `python run_eval.py --bank IMO-AnswerBench`（约 75 分钟）。

1. **无 prefill** → 思维块吃满 token，JSON 腰斩 →「JSON 解析失败」
2. **只用 `'{"'`** → 模型以为已进对象内部，直接吐数组元素，**丢掉 `root_id`/`nodes` 外层包装** →「DAG 结构非法」
3. **锚定种子 `'{"root_id": "g", "nodes": ['`** → 结构完整

实测：3/3 成功，13/8/14 节点，validate 零错误，**26.7s/题**（原 eval_A 为 439.7s/题且 0/3）。

| 项 | 计划初稿估算 | **实测** |
|---|---|---|
| `Mathlib.Tactic` 闭包 | 1.5–3GB（多半走方案 C） | **337 个 olean / 0.11 GB** |

初稿数字来自**按目录统计**（`Mathlib/Tactic` 目录本身 429MB，闭包会拉进
Algebra/Analysis），而真实的**依赖闭包**只有 0.11GB。

**编译探针全部通过**：`import Mathlib.Tactic` 下 `norm_num / ring / linarith /
nlinarith / positivity / omega` 六个 tactic 均可用。

> 结论：**走方案 A，比赛端带 Mathlib 完全可行**，老师 #1/#2 诉求可满足。
> 这也定位了 1.28GB 打包事故的根因——**按目录通配符拷贝，而非按依赖清单拷贝**。

### 发现并修复：PaperPacer 漏乘并发数

`budget_for()` 原式 `paper_cap = 剩余目标时间 / 剩余题数`，**把「墙钟秒」
当成了「单题时长」**。并发=3 时 3 题并行，全卷墙钟 = 总时长 / 3，
单题可用时长应为 **并发 × 剩余墙钟 / 剩余题数**。漏乘导致单题预算只有
真实可用值的 **1/3**。

防超时需要**两道防线缺一不可**（`tools/simulate_paper_budget.py`，
112 题 / 并发 3 / 6h 硬限）：

| 配置 | 全卷墙钟 | 结果 |
|---|---|---|
| 无防线（配额关 + 收紧关） | 6.47h | ❌ 超时 |
| 仅 deep 配额闸 | 6.07h | ❌ 仍超时 |
| 两道防线（**修并发前**） | 2.32h（39%） | ✅ 但大量时间闲置 |
| 两道防线（**修并发后**） | 4.27h（71%） | ✅ 时间真正用起来 |

最坏情况（112 题**全部**想进 deep）：**5.09h（85%）✅**，deep 正确封顶 28 题。

配套修复：`orchestrator.py` 让 `soft_budget` 真正收紧 `ctx.deadline`
（此前算出后无人消费）；`base.py` 的 `is_time_critical()` 硬编码 300s
改为可配置（默认 120s、deep 档 60s）。

测试：151 → **162 全绿**（新增 11 个 PaperPacer 用例，含并发换算回归）。
